# Qwen Image 2.1 로컬 편집 검증 계획

## 문서 상태

- Status: `IDEA`
- 대상 모델: `Qwen/Qwen-Image-2.1`
- 실행 위치: Hugging Face Space가 아닌 개발용 노트북
- 구현 상태: 미구현
- 목적: 후속 실험의 범위와 판단 기준을 미리 고정
- 마지막 갱신: 2026-10-02

## 검증 목적

현재 데모는 기존 가구를 제거한 뒤 잘라낸 2D 이미지를 AR 평면에 다시 배치한다.
이 방식은 빠르고 위치를 정확히 제어할 수 있지만, 이동한 가구의 원근·조명·그림자와
원래 자리의 배경 복원이 서로 분리되어 결과가 합성처럼 보일 수 있다.

후속 실험에서는 Qwen Image 2.1의 이미지 편집 기능으로 다음 가능성을 확인한다.

1. 선택한 가구를 지정한 위치와 크기로 이동할 수 있는가.
2. 원래 가구가 있던 영역을 자연스럽게 복원할 수 있는가.
3. 이동한 가구의 정체성, 재질, 방향을 유지할 수 있는가.
4. 노트북 한 대에서 데모에 사용할 수 있는 시간 안에 처리할 수 있는가.
5. 현재 RGB-D/AR 배치 흐름의 후처리 단계로 사용할 가치가 있는가.

## 이번 실험에서 결정하지 않는 것

- Android 기기에서 Qwen Image 2.1을 직접 실행하는 온디바이스 구조
- Hugging Face Space 또는 외부 유료 추론 API 사용
- 운영 서버, 사용자 인증, 작업 큐, 자동 확장, 과금 구조
- 모델 학습, Fine-tuning, 전용 Move LoRA 제작
- 실시간 카메라 프레임마다 생성형 편집을 수행하는 구조
- Qwen 생성 결과를 즉시 현재 앱에 연결하는 구현

## 전제와 주의사항

- Qwen Image 2.1은 작은 2~3B 모델이 아니다. 양자화는 저장 공간과 메모리 사용량을
  줄이지만 모델의 파라미터 수나 연산량 자체를 같은 비율로 줄이지 않는다.
- 원본 BF16 실행, FP8/INT8 계열 양자화, GGUF는 서로 다른 실행 경로다. 특정 형식을
  먼저 채택하지 않고 노트북 GPU와 지원 라이브러리를 확인한 뒤 비교한다.
- 참고 Space의 UI와 ZeroGPU 실행 환경은 재사용 대상이 아니다. 모델 호출 방식,
  프롬프트, 입력 이미지 구성과 평가 아이디어만 참고한다.
- 생성형 편집은 픽셀 수준의 결과를 만들지만 AR world pose의 정확성을 보장하지 않는다.
  위치 결정은 기존 AR/RGB-D 흐름이 담당하고 Qwen은 이미지 품질 보정 후보로 본다.

## 제안 처리 구조

```text
Android / 기존 데모
  ├─ 원본 키프레임 JPEG
  ├─ 대상 가구 mask 또는 bbox
  ├─ 목표 위치 bbox
  └─ 선택 사항: Depth, plane 종류, 이동/회전/scale
                    │
                    ▼
개발용 노트북의 로컬 검증 코드
  1. 입력 정규화 및 해상도 축소
  2. 원본 위치와 목표 위치를 색상 박스로 표시
  3. Qwen Image 2.1 편집 추론
  4. 원본 해상도·비율 복구
  5. 처리 시간·VRAM·결과 이미지 저장
                    │
                    ▼
오프라인 비교
  ├─ 현재 2D 이동 결과
  ├─ Qwen 단독 편집 결과
  └─ 기존 배치 + Qwen 후처리 결과
```

초기에는 앱과 서버를 변경하지 않는다. 현재 데모에서 저장한 키프레임과 메타데이터를
파일로 복사해 노트북에서 반복 실행한다. 결과가 채택 기준을 통과한 뒤에만 기존
`RemoveObjectProvider`와 별도의 편집 Provider 또는 후처리 단계 추가를 검토한다.

## 노트북 실험 스켈레톤

실제 구현 시 아래 순서로 셀을 나눈다. 이 문서 단계에서는 Notebook이나 의존성 파일을
만들지 않는다.

### 1. 환경 확인

- GPU 이름, VRAM, CUDA, Driver, PyTorch 버전 출력
- BF16, FP16, FP8 또는 선택한 양자화 형식 지원 여부 확인
- 실행 전·후 최대 GPU 메모리와 시스템 RAM 기록
- 모델 캐시 경로와 필요한 디스크 여유 공간 확인

### 2. 모델 로딩

- `QwenImage21Pipeline.from_pretrained()` 기준 경로를 먼저 검토
- 기본 모델과 가속용 LoRA를 분리해 기록
- `device_map`, CPU offload, attention 최적화 적용 여부를 실험 이름에 포함
- 모델 로딩 시간과 첫 추론 준비 시간을 별도로 측정

### 3. 입력 준비

- 원본 이미지의 비율을 유지하고 모델 입력 해상도만 제한
- source bbox는 빨간색, target bbox는 초록색으로 표시
- 정밀 mask가 있으면 bbox 실험과 별도 케이스로 관리
- Prompt, seed, 해상도, step 수를 결과 이미지와 함께 JSON으로 저장

### 4. 편집 추론

- 같은 입력을 최소 3개 seed로 실행해 결과 편차 확인
- 한 번에 한 가구만 이동하는 케이스부터 시작
- 제거, 이동, 크기 변경을 한 요청에 포함한 경우와 단계별 요청을 비교
- Warm-up 이후 순수 추론 시간과 전체 처리 시간을 구분

### 5. 결과 정규화

- 출력 비율과 해상도를 원본에 맞춤
- 대상 영역 밖 변화량을 계산할 수 있도록 원본과 정렬
- 원본, 입력 주석 이미지, 결과, 차이 영상을 같은 이름 규칙으로 저장

### 6. 평가 리포트

- 모델 형식과 설정별 성공/실패 표 작성
- 최대 VRAM, RAM, 로딩 시간, 평균 추론 시간 기록
- 육안 평가와 자동 지표가 충돌하면 실패 이미지를 우선 보존
- 채택, 보류, 폐기 중 하나로 결론을 남김

## 최소 입력·출력 계약 초안

### 입력

```json
{
  "image_path": "cases/living-room-01.jpg",
  "object_type": "sofa",
  "source_bbox": [0.12, 0.42, 0.44, 0.86],
  "target_bbox": [0.52, 0.38, 0.88, 0.84],
  "mask_path": "cases/living-room-01-sofa-mask.png",
  "seed": 42
}
```

`bbox`는 `[x1, y1, x2, y2]` 정규화 좌표를 사용한다. `mask_path`는 선택 값이며,
초기에는 현재 앱이 제공하는 bbox만으로 시작한다.

### 출력

```json
{
  "result_path": "results/living-room-01/qwen-seed-42.png",
  "model": "Qwen/Qwen-Image-2.1",
  "precision": "TBD",
  "width": 1024,
  "height": 768,
  "load_seconds": 0,
  "inference_seconds": 0,
  "peak_vram_mb": 0,
  "peak_ram_mb": 0,
  "status": "PASS_OR_FAIL",
  "notes": ""
}
```

## 검증 데이터셋

최소 10개 장면을 사용하고 장면별로 현재 방식과 Qwen 결과를 나란히 보관한다.

| 구분 | 최소 수 | 확인 내용 |
|---|---:|---|
| 단순 벽 앞 TV·액자 | 2 | 원래 자리 복원, 벽 무늬 연속성 |
| 바닥 위 소파·의자 | 2 | 바닥 접촉, 그림자, 크기 변화 |
| 테이블·선반 | 2 | 가는 다리, 수평·수직 구조 보존 |
| 다른 물체와 겹친 가구 | 2 | 가림 관계와 주변 물체 보존 |
| 저조도·반사·복잡 배경 | 2 | 실패율과 비대상 영역 변형 |

각 장면은 작은 이동, 큰 이동, 0.7배 축소, 1.3배 확대 중 최소 두 조건으로 검증한다.
테스트 이미지는 개인정보와 촬영 위치 정보가 제거된 파일만 사용한다.

## 평가 기준

### 필수 품질 기준

- 목표 중심점 오차가 이미지 폭·높이의 5% 이내
- 목표 bbox 대비 결과 가구 크기 오차가 15% 이내
- 원래 위치에 가구 잔상이나 중복 객체가 눈에 띄지 않음
- 가구 종류, 주요 색상, 재질과 구조가 원본과 같은 대상으로 인식됨
- 대상 영역 밖의 벽, 창문, 다른 가구가 불필요하게 바뀌지 않음
- 결과가 원본과 같은 화면 비율로 복원됨

### 성능 기준

- 한 장 처리 시간이 데모 대기 가능 범위인지 기록하고 팀이 상한을 결정
- 반복 실행 중 Out Of Memory 없이 동일 설정으로 5회 완료
- 모델 로딩 후 두 번째 요청부터 메모리가 계속 증가하지 않음
- 노트북이 배터리 모드가 아닌 고성능·전원 연결 상태에서 측정

### 비교 기준

| 항목 | 현재 2D/RGB-D 방식 | Qwen 단독 | 현재 방식 + Qwen 후처리 |
|---|---|---|---|
| 위치·크기 제어 | 기준선 | 측정 | 측정 |
| 가구 정체성 유지 | 기준선 | 측정 | 측정 |
| 빈 자리 복원 | 기준선 | 측정 | 측정 |
| 원근·조명·그림자 | 기준선 | 측정 | 측정 |
| 처리 시간 | 기준선 | 측정 | 측정 |
| GPU 메모리 | 없음 또는 낮음 | 측정 | 측정 |

## 하드웨어별 실행 판단

실험 시작 전에 노트북 GPU와 VRAM을 문서 상단에 추가한다.

| 조건 | 초기 판단 |
|---|---|
| NVIDIA GPU와 충분한 VRAM | BF16 또는 FP8 경로부터 검토 |
| VRAM 부족, 시스템 RAM 충분 | CPU offload로 기능 검증만 수행 |
| 6~8GB VRAM | 저해상도·양자화 경로만 시도하고 속도를 필수 기록 |
| CUDA 미지원 GPU 또는 CPU 전용 | Qwen 실험을 중단하고 소형 모델/외부 장비 검토 |

CPU offload로 실행되더라도 한 장 처리 시간이 데모 흐름을 깨면 채택하지 않는다.
실행 성공 자체보다 반복 가능한 처리 시간과 결과 품질을 우선한다.

## 주요 고려사항과 리스크

### 정확한 배치 제어

생성형 모델은 초록색 target bbox를 지시로 이해하더라도 픽셀 단위 위치와 크기를 정확히
지키지 않을 수 있다. AR pose와 생성 결과가 다르면 현재 방식의 배치 결과를 기준으로 하고,
Qwen은 경계·조명·배경을 보정하는 제한된 역할로 축소한다.

### 가구 정체성 변화

소파 무늬, 다리 개수, TV 베젤처럼 제품을 식별하는 특징이 바뀔 수 있다. 카탈로그 상품
연결을 유지해야 하는 장면에서는 단순히 비슷한 가구가 생성된 결과를 성공으로 보지 않는다.

### 비대상 영역 변경

전체 이미지를 다시 생성하면 벽 장식, 창문, 다른 가구가 바뀔 수 있다. source와 target
주변을 제외한 영역의 픽셀 차이와 육안 비교를 함께 사용한다.

### 2D와 AR 좌표 불일치

Qwen 결과는 한 카메라 시점의 2D 이미지다. 다른 시점으로 이동하면 깊이·가림·재투영 문제가
남는다. 생성 결과가 좋아도 영구 Spatial Anchor나 3D mesh 문제를 해결한 것으로 간주하지 않는다.

### 메모리와 발열

양자화 파일 크기만 보고 실행 가능성을 판단하지 않는다. Text Encoder, VAE, activation,
입력 해상도와 참조 이미지 수가 추가 메모리를 사용한다. 장시간 반복 시 노트북의 발열과
GPU clock 저하도 함께 기록한다.

### 라이선스와 배포

모델 사용 전에 Qwen Research License의 사용·배포 조건을 다시 확인한다. 모델 파일을 APK나
저장소에 포함하지 않고 로컬 캐시 경로와 라이선스 정보를 분리한다.

### 개인정보와 저장

실내 사진은 생활 공간과 개인정보를 포함할 수 있다. 로컬 실험만 수행하고 EXIF를 제거하며,
원본·결과·로그의 보관 위치와 삭제 기준을 정한다.

## 중단 조건

다음 중 하나라도 반복되면 Qwen 직접 실행 경로를 중단하거나 보류한다.

- 노트북에서 최소 설정으로도 모델을 안정적으로 로드하지 못함
- 동일 조건 5회 중 2회 이상 OOM 또는 프로세스 종료 발생
- 단순 장면에서도 가구 위치·크기 필수 기준을 반복적으로 위반
- 원래 자리 복원보다 주변 물체 변형이 더 크게 발생
- 현재 2D/RGB-D 방식보다 품질 개선이 작고 대기 시간이 크게 증가
- 라이선스 조건이 예정된 시연·배포 방식과 맞지 않음

## 채택 후 예상 연동 지점

검증을 통과하면 다음 구조 중 하나를 별도 Decision으로 선택한다.

1. **독립 편집 Provider**: 서버가 source/target bbox를 받아 Qwen 결과를 생성한다.
2. **후처리 Provider**: 현재 RGB-D/2D 배치 결과를 Qwen이 자연스럽게 보정한다.
3. **오프라인 데모 도구**: 실시간 앱에는 연결하지 않고 대표 결과 생성에만 사용한다.

기존 `RemoveObjectProvider`를 바로 대체하지 않는다. 삭제·복원과 이동·합성은 입력과 실패
조건이 다르므로 실험 결과를 보고 인터페이스 분리 여부를 결정한다.

## 시작 전 확인할 질문

1. 실험 노트북의 GPU 모델과 VRAM은 얼마인가.
2. 사용 가능한 시스템 RAM과 디스크 여유 공간은 얼마인가.
3. 한 장당 허용할 최대 대기 시간은 몇 초인가.
4. Qwen의 역할을 전체 이동 편집과 후처리 중 어디까지 허용할 것인가.
5. 현재 데모에서 source mask와 target bbox를 파일로 추출할 수 있는가.
